# 4章 モジュールの基本
本章の主役はTerraformモジュール。
プログラミング言語において、関数やクラスを切り出して再利用するように、Terraformではモジュールを使って設定をまとめ、再利用できる。

## Terraformにおけるモジュールとは
**Terraformでは、1つのディレクトリにある`.tf`ファイル群がひとかたまりの設定として扱われる。**
このひとかたまりを**モジュール**と呼ぶ。

モジュールには、主に次の2種類がある。
- **ルートモジュール**：`terraform apply`などのTerraformコマンドを実行するディレクトリの設定一式
- **子モジュール**：ルートモジュールや他のモジュールから、`module`ブロックで呼び出されるモジュール

つまり、普段作成している`terraform apply`を実行しているディレクトリも、それ自体が1つのモジュールになっている。

![モジュールの役割](./image/terraform_module_concept.png)

例えば、以下のようなディレクトリ構成を考える。
```
.
├── modules
│   └── hogehoge
│       └── main.tf
└── prod
    └── services
        └── main.tf
```
このとき、`./prod/services/main.tf`から`./module/hogehoge`の内容を呼び出したい場合、
- ルートモジュール：`./prod/services`
- 子モジュール：`./module/hogehoge`

という関係になる。

`./prod/services/main.tf`に`module`ブロックを記載すると、子モジュールの内容を呼び出せる。
※詳細は次章で説明。

```tf
# ./prod/services/main.tf の内容
module "hogehoge" {
    source = "../../../module/hogehoge"
}
```

この`source`は**どのモジュールを読み込むか**を表している。

> sourceについては、ローカルディレクトリだけでなく、Gitリポジトリ上のモジュールを指定することも可能

このように**モジュールとして切り出しておくことで、同じ構成を検証環境用、本番環境用の両方で使い回しやすくなる。**
さらに、環境ごとの差分は変数として外から渡すことで、設定の重複を減らしやすくなる。（※次章で説明）

## 入力変数を利用して、設定内容を変更する
`./module/hogehoge/main.tf`のようなモジュールを利用する場合、検証環境用コードと本番環境用コードで設定値を変えたい場合はどうすれば良いか？

**→ 入力変数を利用する**

Terraformでは、モジュール側に入力変数を定義しておくことで、呼び出し元のルートモジュールから値を渡すことが可能。
これにより、**同じモジュールを使いまわしつつ、環境ごとに設定だけを切り替えることができる。**

![入力変数の利用](./image/terraform_module_variables.png)

#### ▼ サンプル構成

入力変数を利用したモジュールの説明にあたり、以下のようなフォルダ構成を考える。
※ 下記内容は「詳解Terraform」に記載のない、説明用のサンプル構成になります。
```tf
.
├── modules
│   └── s3_bucket
│       ├── main.tf
│       └── variables.tf
├── stage
│   └── main.tf
└── prod
    └── main.tf
```

この例では、`./modules/s3_bucket`が再利用するモジュールであり、`./stage`と`./prod`がそれぞれルートモジュールとなる。

#### ▼ `./modules/s3_bucket`配下の`.tf`ファイルの記載内容

`variables.tf`

まず、モジュール側で**外から受け取る値**を`variables.tf`に定義する。
> 必ず`variables.tf`でなければならないというものではなく、ファイル名や記載ファイルはなんでも良いが、
> 可読性という観点から、variables.tfに記載する
``` tf:variables.tf
variable "bucket_name" {
  description = "作成するS3バケット名"
  type        = string
}

variable "versioning_enabled" {
  description = "バージョニングを有効化するか"
  type        = bool
  default     = false
}

variable "force_destroy" {
  description = "バケット内にオブジェクトがあっても削除できるようにするか"
  type        = bool
  default     = false
}

variable "tags" {
  description = "S3バケットに付与するタグ"
  type        = map(string)
  default     = {}
}
```
`variables.tf`でのポイントは以下。
- `bucket_name`は`default`を持たないため、**ルートモジュール側で指定が必須**
- `bucket_name`以外は`default`を保つため、**必要に応じて上書きする任意項目**


`main.tf`
次に、`main.tf`ではルートモジュールから受け取った変数を`var.変数名`で参照し、実際のリソース定義に利用する。
```tf:main.tf
resource "aws_s3_bucket" "this" {
  bucket        = var.bucket_name
  force_destroy = var.force_destroy

  tags = var.tags
}

resource "aws_s3_bucket_versioning" "this" {
  bucket = aws_s3_bucket.this.id

  versioning_configuration {
    status = var.versioning_enabled ? "Enabled" : "Suspended"
  }
}
```

このように、**値が変わりうる箇所を変数化**しておくことで、モジュール自体は変更せずに、ルートモジュールごとに設定だけを切り替え可能。

#### ▼ `./stage`と`./prod`の`main.tf`の記載内容
ルートモジュール側では、`module`ブロックを使って呼び出すモジュールを指定する。
このとき、`source`には呼び出したいモジュールのディレクトリを記載し、併せてモジュール側で定義した入力変数（本例だと、`bucket_name`・`versioning_enabled`・`force_destroy`・`tags`）に値を渡す。

これにより、**同じ`./modules/s3_bucket`を使いながら、環境ごとに異なる設定値を適用する**ことができる。

`./stage/main.tf`
```tf
module "app_bucket" {
  source = "../modules/s3_bucket"

  bucket_name        = "myapp-stage-bucket-001"
  versioning_enabled = false
  force_destroy      = true

  tags = {
    Environment = "stage"
    Project     = "terraform-module-sample"
  }
}
```

`./prod/main.tf`
```tf
module "app_bucket" {
  source = "../modules/s3_bucket"

  bucket_name        = "myapp-prod-bucket-001"
  versioning_enabled = true
  force_destroy      = false

  tags = {
    Environment = "prod"
    Project     = "terraform-module-sample"
  }
}
```

この例では、stage と prod のどちらも同じモジュールを利用しているが、
- バケット名
- バージョニングの有無
- `force_destroy`の有無
- タグ

をそれぞれ切り替えている。

つまり、**モジュール側では共通の構成を定義し、環境差分はルートモジュール側から入力変数で渡す**、という役割分担になっている。

#### ▼ この構成のメリット
入力変数を利用することで、同じモジュールを複数の環境で再利用できるようになる。
例えば、今回のように stage と prod で使い分ける場合でも、S3バケット作成のロジック自体は1箇所に集約できる。

その結果、
- 同じような .tf を環境ごとに重複して書かなくてよい
- 設定変更時の修正漏れを防ぎやすい
- 「共通部分」と「環境差分」の切り分けがしやすい

といったメリットがある。
