# 3章 Terraformステートを管理する
本章の主役は、`terraform.tfstate`ファイルであり、このファイルの役割から管理方法を解説している。

## Terraform が「新規作成」か「既存更新」かを判別する仕組み

Terraform は、AWS 上のリソースに直接「これは Terraform が作ったもの」という印を付けることはできない。

では、EC2 の設定を変更するコードがあった場合に、
- 新しく EC2 を作成すべきか
- 既存の EC2 の設定だけを変更すべきか

をどのように判断しているのか？

→ 答えは、`terraform.tfstate` ファイルを使っている。

`terraform.tfstate` には次の情報が保存される：
- Terraform 上のリソース名  
  例: `aws_instance.web`
- 実際の AWS 上のリソース ID  
  例: `i-0123456789abcdef0`

つまり、`tfstate` は、**「Terraform が管理しているリソース」と「その AWS 上での実体（ID）」の対応表**として機能する。
![terraform.tfstateファイルの役割](../../image/terraform_tfstate_role.png)

`terraform apply` 実行時には、
- `terraform.tfstate` に書かれたリソース情報
- 実際の AWS アカウント上のリソースの状態
- 現在の Terraform コード（`.tf` ファイル）

を見比べて、次のように判断している：

- `tfstate` に存在しないリソース → 新規作成
- `tfstate` に存在し、AWSアカウント上のリソース情報とコードに差分がある → 既存リソースの更新
- `tfstate` とAWSアカウント上にリソースが存在するが、コードから消えている → リソース削除

![terraform apply実行時の判定フロー](../../image/terraform_tfstate_diagram.png)

## `.tfstate`の保管方法
`.tfstate`には、機密情報が含まれることもあるため、セキュリティの観点からgithubで管理することは推奨されていない。（例：RDSでは、DBのパスワードなどが平文で記載される）

一方、チーム開発時は全メンバーに共有しないと、意図しないロールバックや前のデプロイと重複したリソースが作成されるといった事故が発生する。

そこで、S3などの共有ストレージに保存して共有するのが一般的。

S3に保存する際に注意するのは、State Lockを有効化し、共有ストレージ上にある`tfstate`ファイルを編集できないようにすること。

> 以前はDynamoDBを利用してState Lockを実装していたが、現在はS3 Backend設定に`use_lockfile=true`とすることで、State Lockを有効かできるようになった。（将来的にDynamoDbのState Lock機能は削除される）

また、`tfstate`ファイルはbackend設定をしておくことで、`tfstate`ファイルの保存場所が設定され、リモートの場合は`terraform apply`を実行する際に`tfstate`ファイルをプルリクエストしてくるようになる。


## `terraform.tfstate` の保管方法（チーム開発前提）
![terraform.tfstateの管理概要](../../image/terraform_tfstate_storage.png)

#### ▼ なぜ GitHub 管理が推奨されないか
`terraform.tfstate` には、構成によっては **パスワードやトークンなどの機密情報が平文に近い形で含まれる可能性がある**（例：RDS の認証情報など）。

この性質上、`tfstate` を GitHub にコミットして共有するのは、セキュリティ・運用両面で推奨されない。

#### ▼ チーム開発では「共有」が必要
チームで Terraform を運用する場合、全員が同じ state（同じ `tfstate`）を参照しないと、Terraform の認識がメンバーごとにズレる。

その結果、
- 既に作成済みのリソースを「未作成」と誤認して **重複作成**
- state の整合性が崩れて **意図しない更新／ロールバック**

といった事故につながる。

#### ▼ 一般的な解決策：Remote Backend（例：S3）で `tfstate` を一元管理
そこで、`tfstate` は S3 などの共有ストレージ（remote backend）に置き、**チーム全員が同じ state を読み書きする**形にするのが一般的。

Terraform では `backend` 設定を行い、`terraform init` によって state の保存先を初期化（必要に応じて移行）する。  
以降の `plan/apply` は、remote backend 上の state を参照し、変更があれば更新して保存する。
> `terraform apply`実行時はremote backend上の`tfstate`をプルしてくる。

#### ▼ State Lock（排他制御）を有効化する
remote backend を共有すると、複数人が同時に `apply` するなどして **state を並行更新**してしまうリスクが出る。  これを防ぐ仕組みが **State Lock（ロック／排他制御）**。

S3 backend では、`use_lockfile = true` により **S3 ネイティブのロック（ロックファイル方式）**を利用できる。:contentReference[oaicite:0]{index=0}

> 以前よく使われていた `dynamodb_table` による DynamoDB ロックは、S3 backend のドキュメント上 **Deprecated（非推奨）** とされており、将来のマイナーバージョンで削除される予定がある。:contentReference[oaicite:1]{index=1}

#### ▼ その他
- `tfstate` を置く S3 バケットは **アクセス制御（最小権限）**と **暗号化**を前提にする
- 可能なら **バージョニング**も有効化しておく（誤更新時の復旧に効く） 

## Terraformバックエンドの制限
#### ▼ S3バケット作成
![Terraformバックエンド制限の概要](../../image/terraform_backend_s3_steps.png)
リソースのデプロイ時は、以下の順で実施する。
- `tfstate`を置くS3バケットを作成（前手で必要）
- デプロイ対象リソースを作成
  - バックエンドの設定：`terraform init`
  - リソースの作成：`terraform apply`

また、S3を削除する際は以下の手順で実施する。
- Terraformのコードからバックエンド設定を削除し、`tfstate`をローカルに退避
  - バックエンド設定を削除して、`terraform init`を実行
- S3バケットを削除するための、`terraform destroy`を実行

#### ▼ バックエンド設定
![Terraformバックエンド制限の概要](../../image//terraform_backend_limitation_config.png)
バックエンド設定（下記コード）を全ての`main.tf`に含める必要があり、冗長になりやすい。
```.tf
terraform{
  backend "s3" {
    region = xxx
    profile = xxx
    bucket = xxx
    key = xxx
    use_lockfile = xxx
    encrypt = xxx
  }
}
```

`main.tf`によらない、`bucket`/`region`/`use_lockfile`/`encrypt`などを、外部設定ファイルに分離することも可能。
その場合、Terraformコードはより簡潔にすることができる。
```.tf
terraform{
  backend "s3" {
    profile = xxx
    key = xxx
  }
}
```

## ステートファイルの分離
一般的な開発においては、本番環境/検証環境/開発環境など、Terraformコードを分離する必要がある。
Terraformで環境分離する方法は**ワークスペースによる分離**と**ファイルレイアウトによる分離**が存在する。
- **ワークスペースによる分離**
    同じ設定に対して簡単かつ分離されたテストを行う際に使用。
    具体的には、`workspace=tmp-stg`などを作って試してみて、終わったらすぐに削除するなど。
    ワークスペースの作成方法や切り替え方はGitHubのブランチに近い。
- **ファイルレイアウトによる分離**
    環境間での分離など、明確に分離したい場合に使用する。

#### ▼ terraform workspaceによる分離
terraformにはworkspaceという仕組みがあり、同じ`.tf`ファイル群でも、workspaceを切り替えることで、別の`tfstate`を使ってデプロイすることができる。

workspaceはCLIコマンドであり、コマンドの一覧は以下。
```zsh
# 現在のワークスペースを確認する
% terraform workspace show
default

# workspaceの一覧を確認する
% terraform workspace list
  default
  example1
* example2

# ワークスペースを新規作成する
% terraform workspace new ワークスペース名

# 別のワークスペースに移動する
% terraform workspace select ワークスペース名
```

Terraformコード内で三項演算子などを利用することで、「このワークスペースではこの設定でデプロイ」のような制御が可能となっており、ワークスペースごとに`.tf`を複数作成するといったことは実施しない。

また、バックエンド設定を複数作成しなければ、`tfstate`が上書きされてしまうのではという懸念を抱いたが、これも問題にはならない。
`.tf`のバックエンド設定が`key = "hogehoge/terraform.tfstate"`であり、各ワークスペースで`terraform apply`を実行した場合、以下のように`tfstate`ファイルが保存される。
- `default`ワークスペース
  → `/hogehoge/terraform.tfstate`に保存
- `example1`ワークスペース
  → `:dev/example1/hogehoge/terraform.tfstate`に保存
- `example2`ワークスペース
  → `:dev/example2/hogehoge/terraform.tfstate`に保存
